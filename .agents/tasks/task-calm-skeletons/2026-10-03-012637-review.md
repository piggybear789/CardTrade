# Calmer loading skeletons: reduced inner texture, even visual weight (v1)

This refactor answers the user's note that the loading skeletons carry too much detail and uneven visual weight. The adopted rule is to collapse decorative texture — text-bar widths, decorative shapes, chat-bubble heights — onto a small canonical set while leaving every reserved footprint byte-for-byte intact, so nothing shifts when real data swaps in. The change spans ~30 skeleton/loading files plus a convention note added to `TextLines` in `skeleton.tsx`. Texture-bar widths are normalized to `{w-1/3, w-1/2, w-2/3, w-full}` with a `w-1/3`/`w-1/2` final-line taper; decorative circles used purely as texture become neutral same-size `rounded-md` boxes or are dropped where nothing aligns to them; varied-height chat bubbles become uniform `h-12` on a two-width alternating set; and multi-width "stair-step" label columns collapse to a single uniform width.

The whole review hinges on one invariant from `.kiro/steering/structure.md`: a loader must reserve fixed geometry and never move content outside its own region when data arrives. Every edit was checked against the test "does this width/height reserve space other content lines up against, or is it texture inside an already-sized line box / column?" All reviewed edits touched only the texture side of that line. The one change that is NOT a width swap — dropping `size="lg"` from the home loader's rail CTA — was traced through the shell and found to be a correctness fix (it brings the skeleton into agreement with the real page, and the on-screen height is unchanged because the shell wrapper forces it).

Watch for: nothing blocking. The `size="lg"` removal on `(home)/loading.tsx` looks at first glance like a geometry change but is not (confirmed). The two palette-tone edits in `SettingsPrimitives.tsx` (`pending` tone) are prior-session theme work that rode along in the same file, out of task scope, and are flagged only so they are not mistaken for skeleton geometry.

**Verdict**: APPROVED

## High-level view

Geometry preservation is the gating concern, and it holds across the change. Every edit falls into one of three safe buckets: a bar width inside a line box whose height comes from a `text-*` type-scale class; a bar width inside a `min-w-0`/`flex-1` column that nothing else aligns to; or a decorative shape that sets no height. In each case the thing that actually reserves space — the type scale, a `min-h-*`/`h-*` floor, a `size-N` box in its own column, an aspect frame, a `md:`/`sm:` visibility gate, a fixed grid template, a `line-clamp-N` + `min-h-[Nlh]` pair, or a `ch`/`[Nlh]` reservation — is left verbatim, and the comments mostly call out which part is the reserve.

The home loader was the file most worth scrutinizing because the briefing singled out its mobile hub strip and desktop genre-pill track as load-bearing. Both are left verbatim (the pill widths `w-16…w-44` on `h-11`, and the `GenreStripSkeleton` cell geometry). The only non-width edit there, `size="lg"` dropped from `RailPrimaryAction`, is safe: that CTA renders only in the desktop rail (`hidden md:block`), where `MarketplaceShellSkeleton` wraps it in `md:[&>a]:!h-11 … md:[&>a>svg]:size-4` — an `!important` height that wins over any `size`. The real `(home)/page.tsx` itself passes no `size` prop, so the skeleton now matches the page rather than diverging from it.

Texture-uniformity is applied consistently: chat logs in `ContractRoomSkeleton` and `ChatThreadSkeleton` all converge on uniform `h-12` bubbles with an incoming-`w-2/3` / outgoing-`w-1/2 ml-auto` alternation and unchanged bubble counts; the contract room's six-row detail list and four-tab strip collapse their per-item width spreads to single uniform widths; and `listings/mine`'s six-value `ROW_TITLE_WIDTHS` becomes a two-width alternation. The convention is documented once in `TextLines` so future loaders inherit it.

Comment accuracy is good and unusually load-bearing in this codebase — several comments encode measured pixel reservations. The edits update the comments in step with the widths and consistently restate which dimension is the reserve. One decorative-circle drop (the contract header's second avatar+name pair) and two "kept as neutral reserve" decisions (the inbox-row avatars) are explained in the comments with the correct reasoning about what sets the row height.

### Geometry preservation — the reserved footprint is intact everywhere

The structure rule is that arriving data must not move anything outside its own region, so the only safe edits are to widths/heights that are texture: a bar inside a line box sized by its `text-*` class, a bar inside a `min-w-0`/`flex-1` column nothing aligns to, or a decorative shape that contributes no height. Every reviewed edit is one of those.

Type-scale line boxes are preserved while their bar widths move. `AuthFormSkeleton` keeps `text-head leading-none`, `text-subhead`, every `h-11`/`h-9 md:h-8` field, every `min-h-11` touch-target row, the `sm:hidden` on sign-in's second description line, and the `size-5` checkbox — only the fractions inside change. `ItemFormSkeleton` keeps the 108px `Textarea rows={4}` reserve, the `h-9 md:h-8` field heights, the one-layout-at-every-width photo grid, and the edit-mode-only immutability line; the label widths collapse to `w-1/3`/`w-1/2`. The marketing and help loaders keep their `md:`-gated line counts and the `line-clamp`-driven paragraph line arrays, tapering only the final line.

Load-bearing responsive gates survive. `md:hidden` / `hidden … md:block` pairs that reserve an extra wrapped line below a breakpoint are kept throughout: the listing-detail meta line (`w-1/3 md:hidden`), the payouts caption (`md:hidden` four-line vs `md:block` two-line), the admin `QueueIntroSkeleton` (`index >= desktopLines ? md:hidden`), the arbitration reason line, and the home header count (`hidden … sm:block`). In each the gate is untouched and only the fraction behind it changes.

Fixed-dimension reserves beside texture are kept. The listing-detail carousel's `aspect-[4/5]` frame, the `line-clamp-4` + four-line description reservation, the `min-h-10` Read-more target, condition pill `h-5 w-16`, and the seller `size-10` avatar are all intact. `CheckoutSummarySkeleton` / `SavedCardRow` keep their `size-5` glyph and `h-8 … md:h-7` button; `EmbeddedPayoutStep` keeps both `h-10` field reserves. The `listings/mine` table keeps its grid template, the `border border-transparent` focus reserve that makes the title line 24.4px, and the badge `h-[1.425rem]`.

`ch`/`[Nlh]`/`size-N` reservations that position other content are untouched. The onboarding and auth files keep their `h-[0.9em] … align-middle` inline bars (only the trailing fraction changes), the sellers loader keeps `h-[1.175rem]` and `min-h-6` rows, the arbitration back-link keeps `min-h-11`, and `OnboardingSpineSkeleton` keeps its two-line body wrap as the reservation.

The `SettingsRowSkeleton` default change (`labelClassName`/`valueClassName` `w-28`/`w-20` → `w-1/3`) is safe because the row's height is set by `min-h-12`, the icon medallion, and the `description` flag — none of which the label/value widths touch. All `AccountHubSkeletons` call sites that previously passed pixel widths now pass `w-1/3`, and the load-bearing `description` flags and `valueClassName="hidden"` collapses are preserved.

### The home rail CTA `size="lg"` removal — traced, and safe

`app/(workspace)/(home)/loading.tsx` changed `<RailPrimaryAction href="/listings/new" size="lg">` to drop `size="lg"`. On its face this alters a control height, which would be a geometry regression. It is not, for two independent reasons that both check out in the source:

- The CTA renders only in the desktop rail. In `MarketplaceShellSkeleton`, `primaryAction` sits inside `<div className="hidden md:block">`, and the wrapper is `className="mt-group md:[&>a]:!h-11 md:[&>a]:text-body md:[&>a>svg]:size-4 …"`. The `!h-11` important rule forces 44px regardless of what `size` sets on the underlying `Button`, and the glyph/text are likewise pinned. This wrapper is identical to the one in the real `MarketplaceShell`.
- The real page does not pass `size` either. `(home)/page.tsx` builds its `primaryAction` as `<RailPrimaryAction href="/listings/new">Create New Listing</RailPrimaryAction>` with no `size`, and its comment notes the override "lands on desktop only." So before this edit the skeleton was passing a prop the real page omits; the edit removes a divergence rather than creating one.

The net on-screen footprint is unchanged, and skeleton/page now agree. `RailPrimaryAction`'s own JSDoc argues the catalog CTA "wants" `lg`, but that argument is about the live rail where the shell applies the same `!h-11`; the prop is inert at the breakpoint it renders on.

### Texture uniformity — chat logs, detail rows, tab strips

The chat-bubble treatment is the clearest expression of the "even visual weight" goal and is applied the same way in all three logs. `ContractRoomSkeleton`'s phone and desktop logs and `ChatThreadSkeleton`'s log all become uniform `h-12 rounded-2xl` bubbles on an incoming-`w-2/3` / outgoing-`w-1/2 ml-auto` alternation, replacing the old mix of `h-10`/`h-12`/`h-16` and `w-2/5`/`w-3/5`. The bubble counts (3, 5, 4), `gap-cozy`/`space-y-cozy`, `justify-end` anchoring and `rounded-2xl` are unchanged, and the log sits in a `flex-1` region whose height is set by the fixed bands around it — so bubble dimensions are genuinely texture here.

The contract room's detail panel had the single biggest texture spread in the change: a six-value label column (`w-24 w-20 w-28 w-16 w-24 w-20`) and a four-value tab-label row (`w-10 w-12 w-14 w-16`). Both collapse to one uniform width (labels `w-20`, tabs `w-12`), and the comments correctly note that the `min-h-11` tab cells, `space-y-group`, `items-baseline`, cell/row counts, and the `shrink-0`/`min-w-0` column roles are what hold the geometry — the widths never positioned each other. `listings/mine`'s `ROW_TITLE_WIDTHS` makes the same move from a six-value spread to a `w-2/3`/`w-1/2` alternation.

### Decorative-shape handling — one drop, two deliberate keeps

The contract header's party cluster drops its second avatar+name pair and collapses the first `size-6 rounded-full` circle to a neutral `size-6 rounded-md` box. This is justified: the cluster lives in a `flex-wrap` row whose height is set by the `text-body` line and the badge beside it, not by the 24px circles, and the right-hand badge+money group is `shrink-0` under `justify-between`, so shortening the left cluster moves nothing. Reducing `rounded-full` to `rounded-md` also drops final-shape mimicry, matching the stated rule.

The two `InboxRowSkeleton` avatars (`size-12 rounded-full` and the wide row's `size-6` + `h-5 w-16` pill) are explicitly KEPT as same-size neutral reserves rather than dropped, even though by the height test they are decorative. The comment's reasoning is sound: the surrounding comments record a measured 65.6px row height that these boxes contribute to, so the conservative move is to touch only the text widths. This is the right call — dropping them would risk the measured reservation the file was built around.

### Comment accuracy

Comments in these files encode measured pixel reservations (e.g. "the old bars came to 56px against the row's 65.6px", the 108px textarea, the 44px recovery-link row), and this codebase treats stale geometry comments as a real hazard. The edits update prose in step with the widths and repeatedly restate which dimension is the reserve vs the texture, which keeps the comments trustworthy. The new `TextLines` convention block states the width-is-texture rule and the canonical set once, and correctly carves out `ch`-sized and `w-N` load-bearing widths as the exception that stays exact. No comment was found asserting a reservation that its own edit then violated.

### Scope note — palette edits in `SettingsPrimitives.tsx`

Two lines in `SettingsPrimitives.tsx` change the `pending` status tone from the `iris` palette to neutral `border/muted/foreground`, in both `TONE_CLASS` and `IconMedallion`. These are theme/palette changes from the prior session, not skeleton geometry, and are outside this task's scope. They are harmless to the skeleton work (the only in-scope edit in this file is `SettingsRowSkeleton`'s default widths) but are flagged so they are reviewed under the palette change rather than attributed here.
